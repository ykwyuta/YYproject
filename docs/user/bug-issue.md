# バグ管理・課題管理と統計

「編集 → バグを追加」「編集 → 課題を追加」で登録し、「バグ一覧」「課題一覧」で別々に管理します。既存の課題は同じID・状態・関連タスクを保持します。通常のタスク一覧・カンバン・ガントからは分けて表示します。全種類の全文検索や依存ネットワークでは関連する項目を横断して確認できます。

一覧ではセル選択、F2編集、コピー・貼り付け、列境界・行境界のドラッグ、ID列からの行移動が使えます。列の右クリックで原因分類・工程・担当者などの値を絞り込めます。Shift／Ctrlによる複数行の選択と属性一括編集も共通です。担当者・カテゴリ・状態・優先度・期限に加え、工程・原因・難易度・対策予定日時・完了／中止日時も一括編集できます。件名などの個別項目を複数行で一括上書きすることはできません。工程・原因・難易度は同列の範囲を選択してCtrl+Dでコピーできます。

行を選び「編集 → 選択項目を編集」で詳細フォームを開きます。タブで基本情報、工程・原因・難易度、暫定対策、恒久対策、発生・検出・報告、対策日時、確認・関連、説明、レビューを切り替えます。

|分類|記録内容|
|---|---|
|基本|件名、カテゴリ、担当者、状態、優先度、重大度、説明|
|分析|発生工程、原因分類、検出工程（自由入力）|
|対策|暫定対策案、恒久対策案・案件（複数行）、対応タスクID（カンマ区切り）|
|難易度|暫定対策・恒久対策・検知それぞれ未指定／低／中／高／非常に高|
|日時|発生、検出、報告、分析、暫定対策予定・実施、恒久対策予定・実施、確認、完了・中止|

日時は `2026-10-27T09:00:00+09:00` のようにタイムゾーンを付けて入力します。保存・日別統計はUTCへ統一します。この例は `2026-10-27T00:00:00Z` と表示されます。任意の日時は空欄にできますが、記録済みの検出日時は消去できません。検出前の実施日、逆転した発生・検出日時、状態履歴より前への完了日時などは保存できません。予定に遅れた実施日時は保存できます。

新規登録時の検出日時は現在時刻です。完了・中止時に日時が空欄なら保存時刻を記録します。再オープンすると完了・中止日時を解除し、過去の状態変更は履歴に残します。詳細フォームでは進捗も再開可能な値へ戻します。既存の完了条件（先行項目・レビュー）は有効です。日時を修正しても後続の状態変更より後へ検出日時を移すことはできません。記録済みのバグと課題の種類変更はできません。

新規GUI登録のバグ・課題は工数集計から除外します。対応作業は関連タスクとして登録してください。既存の課題の工数設定は維持します。MCPから登録するときは `include_in_effort: false` を指定してください。

## 収束と原因分析

「バグ統計」「課題統計」は種類を分けて表示します。「統計設定 → バグ・課題の集計期間」でUTCの開始日・終了日を選択できます（最大10年）。初期表示は、対象の最初の記録日から今日までです。10年を超える場合は直近10年に制限します。

- 日ごとの未完了件数のバーンダウン：未着手・進行中・保留を未完了とし、完了・中止を除きます。再オープンすると未完了へ戻ります。日次格子、週ごとの日の表示、曜日／日／月／年、休日背景、太い線で表示します。
- 終了日時点の検出総数・未完了・完了・中止件数と、完了項目の平均解決時間を表示します。平均解決時間は検出から最後の完了までで、中止や再オープン中は含めません。
- 原因分類・発生工程・検出工程・暫定対策難易度・恒久対策難易度・検知難易度を件数順の棒グラフと割合で表示します。上下・左右にスクロールできます。原因などが空欄なら「未分類」です。

現在の列フィルタ・担当者・カテゴリ・状態・検索などが集計対象に適用されます。分類グラフは現在の属性を使用し、集計終了日までに検出した全対象を数えます。集計開始日より前から未完了だった項目も残件へ引き継ぎます。期間中に新規検出された項目だけを数えるグラフではありません。将来の収束予測や理想線ではなく、記録した状態履歴の件数です。

日時がない旧課題は「日時未記録」として別表示し、日別件数・分類・平均には含めません。詳細を保存すると検出日時が入り、以後の履歴を記録します。保管項目は通常集計から外れ、保管済みフィルタを選べば別に集計できます。保管前のグラフを固定するものではありません。

## CSV・MCP・保存

「ファイル → バグ一覧をCSV出力／課題一覧をCSV出力」、またはバグ／課題の一覧・統計から「ファイル → プロジェクトをCSV出力」を開くと、専用の分析列・日時も出力項目に選べます。種類・検索・担当者・カテゴリ・状態・列フィルタで対象を限定できます。

MCPでは `project_change` の `save_task` に `kind: "bug"` または `"issue"` と `case` を渡します。既存項目の更新前には `project_get` で全属性と最新revisionを読み直してください。`case.transitions` はサーバー管理で、保存要求で削除・書き換えできません。`task_list` の `kind` や `columns: {"case.cause": "仕様漏れ"}` で検索できます。

読み取り専用の `case_statistics` は次の引数を受け取り、GUIと同じ集計結果を返します。stdio／PAT付きHTTPとも共通です。

```json
{"project_id":1,"kind":"bug","from":"2026-10-01","to":"2026-10-31","filter":{"category":3}}
```

SQLiteとPostgreSQLの両方に対応し、相互移行・SQLite書き出しは状態履歴も含めて保持します。DB形式は5です。SQLiteの形式1〜4、PostgreSQLの形式3〜4は読み込め、正常な書き込みと同じトランザクションで5へ更新します。読み取りや拒否された更新では版を変更しません。形式5へ更新したDBは旧アプリでは開けないため、更新前に終了済みDBのバックアップを残してください。
